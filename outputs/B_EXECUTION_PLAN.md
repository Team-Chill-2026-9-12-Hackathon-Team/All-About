### B2：API、任务与事件层（目标 1–3h）

目的：即使 C/D 未交付，也能验证前端与后端的通信。

必须实现的接口：

| 接口 | 行为 |
|---|---|
| GET /api/health | 健康检查，无凭据 |
| GET /api/sources | 仅返回 id/label/kind/access |
| POST /api/runs | 校验 QueryInput；202 返回 runId、eventsUrl、queued |
| GET /api/runs/:id | 返回状态、最新 bundle、last seq，以及双方确认后的清理状态 |
| GET /api/runs/:id/events | SSE，补发遗漏事件后接收新事件 |
| POST /api/runs/:id/clarification | 校验 scopePatch 和 answer；仅 needs_input 可调用 |
| POST /api/runs/:id/cancel | 已知 run 幂等 202；终态不回退 |

实现原则：内存 RunStore 即可；同一演示实例仅允许一个活动 run；非法请求 400，未知 run 404，活动冲突或不允许的状态操作 409。GET 状态接口的具体字段需写入共享 schema，不能各自猜测。

SSE：`id: runId:seq`、`event: type`、`data: JSON`。同 run 序号严格递增；先保存事件再通知订阅者。处理“读历史与订阅之间恰好出现新事件”的竞态；定义无效、跨 run、超前游标的响应并写入 API 文档。

验收：POST 后延迟连接仍收到完整历史；重连只补发需要的事件；活动冲突生效；已完成任务可 GET 恢复；断线不自动取消任务。

交付：真实 HTTP/SSE 与 RunStore。此阶段可用内部测试驱动模拟执行；对外运行模式的处理见 U3，不能冒充实时浏览。

### B3：编排与生命周期层（目标 3–6h）

目的：稳定地按顺序调用模块，并正确停止。

工作：
- 注入 collectPages 和 buildAnswer；默认先在测试中使用可替换 mock，真实运行的依赖缺失时清楚报未配置。
- 实现 queued → planning → needs_input/planning → browsing → synthesizing → completed/partial/failed；活动状态可进入 cancelling → cancelled。
- 浏览器信号映射公共事件；D 结果经校验后发 answer_ready。不要在 B 再调用模型重写事实结论。
- 每个 run 一个 AbortController；取消和处理超时传递给 C/D，迟到结果不能写回已终止任务。
- 澄清等待最多 5 分钟；澄清前不启动浏览器。90 秒处理预算与等待澄清时间分别计时，具体时钟规则先按 U5 记录。
- 取消已有终态 run 仍返回幂等结果，不修改原 completed/failed 状态。
- C 负责远端会话释放；B 只协调和报告。处理结束与清理完成分别记录。

验收：执行中取消、重复取消、C 延迟返回、D 忽略 abort 后迟到、单来源失败、总超时、澄清过期；均无状态倒退或旧结果污染。清理失败可见，不能显示“已释放”。

交付：可通过接口调用的离线流水线及生命周期测试。U1/U2 未确认时，相应真实取消/清理验收标为阻塞，其他路径继续完成。

### B4：查询规划与结果校验层（目标 3–9h；歧义完善至 18h）

目的：把自然语言限制到已支持来源内，并拒绝损坏的答案。

工作：
- 安装官方 OpenAI SDK；模型 ID 从 `OPENAI_MODEL` 读取。不要把执行本任务的 Terra/Sol 名字自动填成应用运行模型 ID。
- 用结构化输出解析对象、requestedFields 和候选 sourceIds；服务端再从 D 的 registry 构造 QueryPlan。模型不能凭空增加 URL 或域名。
- 学校、学期或对象存在无法排除的歧义时提一个澄清问题；不机械要求活动查询也必须有课程字段。
- 校验 sourceIds 存在、scope 适用、访问状态和运行模式；未配置来源与访问失败保持不同含义。
- 默认最多 3 个来源、3 个页面、6 次导航/点击、90 秒活动处理预算；页面上限是新增的保守初值，C 可提出调整。重试应计入总预算。
- 校验 AnswerBundle.runId/mode 与当前 run 一致，ID 唯一，所有 claim/evidence/snapshot 引用存在且属于本次结果；supported claim 有证据，quote 经空白规范化后存在于快照正文。
- 语义支持性、教师角色和日期冲突规则归 D；B 不能用“schema 通过”宣称事实正确。scope/date 等结构不变量可在 B 的边界校验中拒绝。
- 无法回答全部字段时保留可验证内容并输出 partial/unknown；模型失败不返回预置 gold answer。
- 只记录去敏的耗时、调用次数、服务返回的用量数据和错误类别。

验收：同题改写、未知来源 ID、编造 URL、错误学期、需澄清、模型超时、无效结构、跨 run 引用、不存在的引文。真实模型测试使用极短输入并记录实际模型 ID；模型未选定时先完成离线测试。

交付：planner、模型配置入口、结果验证器和错误处理。D 模型失败后如需展示原文卡，先按 U6 确认输出协议。

完整仓库 URL：**https://github.com/Team-Chill-2026-9-12-Hackathon-Team/All-About**。

工作分支：优先沿用团队已分配给 B 的分支；未分配时采用原始计划建议的 `feat/orchestrator`，首次读取远端状态后记录。仓库目标已经由用户明确，无需重复询问；不新建同名 GitHub 仓库。

触发规则：每完成一个可独立说明、经过相应检查的小进度，就 commit 并 push 到 B 的工作分支。无需等 B0–B6 某一整层全部结束；也不是每编辑几行就提交。接口尚待队友确认的提案可以作为明确标注的提案提交，但不能宣称接口已冻结。

建议提交切分：

| 阶段 | 可单独同步的小进度示例 |
|---|---|
| 计划 | 分层计划及 GitHub 协作规则完成并复核 |
| B0 | workspace 配置；后端 health 接口；环境加载与启动说明 |
| B1 | 输入与来源 schema；答案 schema；事件联合类型与样例 |
| B2 | 创建/查询 run；SSE 历史补发；重连与冲突处理 |
| B3 | C/D 注入流水线；取消；超时与迟到结果隔离 |
| B4 | planner；来源限制；答案引用校验；模型失败处理 |
| B5 | C 接入；D 接入；A 联调；真实主路径验收 |
| B6 | 启动/重置说明；去敏回放；展示版本记录 |

每个小进度的执行顺序：

1. 完成一个范围明确的变更，执行与其风险相称的检查。文档修改做内容复核；接口/功能修改跑相关测试和必要的类型检查。检查失败先修复，独立完成且已通过检查的其他变更可分开提交。
2. 检查 Git 状态和暂存差异，只暂存本次 B 的改动以及本计划，不混入队友或无关修改。确认 `.env`、真实凭据、私有会话链接和不必要日志未被暂存；不能仅依赖 `.gitignore` 来保护已被跟踪的文件。
3. 更新 `docs/B.md` 的完成内容、检查与待确认问题，一同提交。提交信息描述具体成果，例如 `feat(server): add run creation endpoint`、`fix(server): ignore results after cancellation`、`docs(plan): define incremental GitHub sync`。
4. 将提交推送至已核实 remote 的 B 分支。已有 upstream 时沿用，首次推送时显式指定正确远端与分支。遵守仓库现有检查规则，不跳过检查、不强推。
5. 验证目标远端分支包含本次提交，向用户报告提交号和推送状态。提交号与最终同步状态可记录在下一次进度交接中，无需为了写入自身提交号反复产生提交。
6. 遇到远端更新，先读取并比较分支；只在保留已有工作的前提下处理可明确解决的集成问题。权限、分支保护或不明确的冲突阻塞时，报告实际原因并保留本地成果。不能把本地 commit 说成 GitHub 已同步。

正常的持续同步无需再次询问用户是否允许推送；仓库地址不明确时需要的是目标信息。GitHub Project 看板更新、自动创建 issue/PR、发布部署和合入主分支不包含在这项同步规则内。如团队仓库已有明确分支流程，执行前读取并遵循，存在冲突时告知用户。
